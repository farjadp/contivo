# B8: quality gate on manually generated drafts

Status: built on `myca/b8-manual-quality-gate` (see Build notes). Owner: contivo-backend-developer; migration by contivo-database-engineer.
Source: QA E2E handover 2026-11-22, B8. CPO decision 2026-11-22: own branch off main, new column (not `failedReason`), override button approved with audit + plain-language reasons.

## Problem

Only `lib/autopilot/runner.ts` calls `evaluateDraft` (`lib/autopilot/quality-gate.ts`). Drafts generated by hand are never judged:

- Ideation → Generate Preview (`generateDraftPreviewCore`)
- Add to Pipeline with the preview (after #31: the preview is saved as GENERATED)
- Pipeline → Generate (`generateDraftForItem`, which also sets SCHEDULED straight away)

On production, a manual draft left no `quality_gate` row in `ai_usage_logs`. The product, and the posts it writes, say a draft "doesn't publish until it clears". That's only true on Autopilot.

## Decisions

1. **Gate every AI draft generated by hand, exactly once per generated text.** "Write a post" (the customer's own text, no AI) stays ungated.

2. **Where the gate runs.**
   - **Generate Preview:** after generation, run `evaluateDraft`. Return `{ preview, verdict, verdictToken }`. The preview modal shows a pass, or a fail with the reasons.
   - **Add to Pipeline with a preview: no second call.** The server can't trust a verdict sent back by the client, so the preview action returns `verdictToken`: an HMAC (key `JWT_SECRET`) over `sha256(previewText)`, the verdict, `workspaceId` and an expiry 30 min out. On save, a valid token whose hash matches the text being saved is stored as the verdict. Otherwise (no token, expired, or the text changed) the item is stored as `not_checked` (see 3).
   - **Pipeline → Generate,** manual path only (`options.source !== 'autopilot'`): run the gate after humanize and before the update.
     - Pass: today's behaviour (SCHEDULED with a slot).
     - Fail: save the body as GENERATED with `scheduledAtUtc = null` and store the verdict. A failed draft must never be left SCHEDULED, or the cron would publish it.
   - **Autopilot:** its gate and retry loop are unchanged. It also writes `qualityVerdict`, so every path reads the same field.
   - **Gate context:** the same as the runner passes.
     - `brandSummary`, `channel`, `topic`
     - `language`: the workspace's `contentLanguage`
     - `storyline`: `loadStorylineContext(item.storylineId)`
     - `recentContents`: the last 10 scheduled/published bodies, using the runner's query
     - `aiContext`: the actor
     - `avoidTopics`: none on the manual path (it's an autopilot policy field)

3. **Persistence: one additive migration.** Add `content_items.qualityVerdict Json?`: nullable, no default, no backfill.
   - Shape: `{ approved, rejectedBy, reasons[], scores, judge, judgeModel, checkedAt, source: 'preview' | 'pipeline' | 'autopilot', override?: { userId, at } }`.
   - `null` means "not an AI draft gated by this system": legacy items and "Write a post" items. They behave exactly as today.
   - An AI path never leaves it null. When it can't judge, it stores `{ approved: false, rejectedBy: 'not_checked' | 'gate_unavailable', ... }`.
   - Don't use `failedReason`: it means "publishing failed", and the UI and reports read it that way.
   - Add the migration to the CLAUDE.md streams table.

4. **A blocked item** is one where `qualityVerdict` is non-null and `approved !== true`.
   - **Pipeline card:** shows a badge, "Quality check failed" or "Not checked", with the reasons expandable. On this card, Approve, Publish and Quick-schedule are replaced by **"Publish anyway…"**.
   - **Confirm dialog:** lists the gate's reasons in plain language, in en and native fa (written in Persian, not translated; see the Persian copy standard). Confirm button: en "Publish anyway", fa «با این حال منتشر کن».
   - **Enforced on the server, not only in the UI:** every server action that moves an item to READY or SCHEDULED (`updateContentStatus`, schedule, quick-schedule, publish-now) refuses a blocked item with `quality_gate_blocked`, unless the request carries `override: true`.
     - An override writes `qualityVerdict.override = { userId, at }`.
     - It also writes an `activity_logs` row `QUALITY_GATE_OVERRIDDEN` with `{ itemId, rejectedBy, reasons, judgeModel }`.
   - **Editing the body of a gated item** sets the verdict to `not_checked` (the verdict judged different text). The card offers "Check again": one gate call, an explicit user action, never run automatically on save.

5. **Gate unavailable** (judge provider chain down → `judge: 'unavailable'`): store it as a fail with reason `gate_unavailable` ("the quality check could not run"). The user can override it. It is never a silent pass.

6. **Cost and observability:** one gate call per generated text. It is logged in `ai_usage_logs` under the existing feature name `quality_gate`, attributed to `{ userId, workspaceId }`.

## Out of scope

B9 (cost/provenance), B10 (discovery), the gate thresholds themselves, the autopilot retry loop.

## Tests (written first)

- **Preview:** `evaluateDraft` is called once with runner-equivalent context, and the response carries the verdict and a token. A provider failure gives `approved: false, rejectedBy: 'gate_unavailable'`.
- **Save with a preview:**
  - A valid token stores the verdict, with no gate call.
  - Tampered text, or an expired token, gives `not_checked`, with no gate call.
- **`generateDraftForItem`, manual path:**
  - Pass: SCHEDULED.
  - Fail: GENERATED, `scheduledAtUtc` null, verdict stored.
  - Autopilot source: unchanged (the runner tests stay green).
- **Status/schedule actions:**
  - A blocked item is refused with `quality_gate_blocked`.
  - With `override: true` it succeeds and writes both `QUALITY_GATE_OVERRIDDEN` and `qualityVerdict.override`.
- **Ungated items:** "Write a post" items and legacy rows (`qualityVerdict` null) schedule as today.
- **Editing:** editing a gated body sets `not_checked`.
- **i18n:** en/fa/it keys exist for the badge, the dialog and the reasons.

## Build notes (where the build differs from the text above)

- **Unavailable codes:** the gate already returns `judge_unavailable` when no judge answers; that is stored as is. `gate_unavailable` is stored when the gate itself throws. Both are fails and both read as "the quality check could not run".
- **"Publish anyway" lifts the block, then the post is scheduled normally:** it calls `updateContentStatus(id, 'READY', { override: true })`. The override stays on the verdict until the text changes, so rescheduling does not ask again.
- **The editor never refuses a save:** `updateContentAndSchedule` on a blocked item (or on a gated item whose body changed) saves the text and holds it as GENERATED with no schedule, instead of throwing. Approve, schedule and quick-schedule do refuse with `quality_gate_blocked`. Moving to DRAFT or ARCHIVED is never gated.
- **Failed scores are stored as `below[]`** at save time, so the UI can name them in the reader's language without importing the thresholds.
- **Strings:** all five app locales (en, fa, it, es, he) carry `tabsA.quality`, because check-i18n requires them in sync.
